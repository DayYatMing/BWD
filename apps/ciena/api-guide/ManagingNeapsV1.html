NEAPS Resource Definitions

A NEAPS resource allows the definition of a unique NE Audit profile capability that can immediately be used with the Audit application.

NEAPS Process Definitions

The NEAPS process definitions are all captured in the processSpecifications NEAPS top-level attribute. These process definitions are used to describe the following two NE Audit workflows:

  • audit process:

    • retrieve the NE audited data using the audit scripts

    • compare the NE audited data with selected custom profile to generate finding details (sent to audit application)

  • fix process:

    • execute the fix scripts as protocol command templates rendered using:

      • the selected custom profile data

      • the audit finding details for some special patterns (e.g. explicit deletion, keep NE value)

NEAPS REST APIs

All REST APIs for the management of the NEAPS resources are documented as Swagger API documentation in the Navigator MC APIs Network element configuration section under NEAPS v1. See below picture.

NEAPS Retrieval

The following REST APIs are used for the retrieval of the NEAPS resource(s):

Multiple (partial) NEAPS Query

GET /configmgmt/api/v1/neaps

  • To retrieve all matching partially populated (summarized) NEAPS resources (with only Core attributes)

  • Following parameters can be used to match/query NEAPS resources:

    • neFunction - Full matching entry with all NEAPS neFunction

    • neTypeGroup - Full matching of one neTypeGroup instance of all NEAPS neTypeGroups

    • neProtocol - Full matching entry with all NEAPS neProtocol

Examples:

  • /configmgmt/api/v1/neaps?neProtocol=tl1 GET all summarized NEAPS using TL1 NE protocol

  • /configmgmt/api/v1/neaps?neTypeGroup=PN10x GET all summarized NEAPS supporting PN10x product family

  • /configmgmt/api/v1/neaps?neFunction=TACACS GET all summarized NEAPS supporting TACACS NE function

Single (full) NEAPS Query

GET /configmgmt/api/v1/neaps/${id}

  • To retrieve the full NEAPS resource identified by its ${id}

NEAPS Creation

POST /configmgmt/api/v1/neaps

This REST API creates:

  • the NEAPS resource using all attributes found in the request payload/body

  • all associated resources. See NEAPS Associated Resources

Notes:

  • The following resource attributes can be omitted as ignored by NEAPS creation implementation:

    • id it is generated by the Navigator MC server and is provided in the created and returned NEAPS instance

    • type it is expected to be neAuditProfileSpecifications

  • NEAPS to be created will be rejected if its resource core definitions overlap with an existing NEAPS

    • See NEAPS Core Definitions

  • GCS parameter controls the maximum number of managed NEAPS *

    • If this limit is reached user can either delete some un-used NEAPS resources or modify the GCS value

NEAPS Modification

PUT /configmgmt/api/v1/neaps/${id}

This REST API updates:

  • the NEAPS resource identified by the ${id} using attributes found in the request payload/body

  • all associated resources. See NEAPS Associated Resources

Notes:

  • the NEAPS core attributes used for the unique identification of the NEAPS cannot be changed. Any changes of their value in the request payload will be omitted. The reason is the REST PUT API should not be changing the ${id} of the updated NEAPS resource.

  • The REST POST API shall be used if the user intent is to update an existing NEAPS unique identification core attributes.

  • This REST API is subject to the NEAPS Update Validation

NEAPS Deletion

DELETE /configmgmt/api/v1/neaps/${id}

This REST API deletes:

  • the NEAPS resource identified by the provided ${id}

  • all associated resources. See NEAPS Associated Resources

Notes:

  • This REST API is subject to the NEAPS Update Validation

NEAPS Testing

Any managed NEAPS resources can be tested using the NEAPS REST test operation.

POST /configmgmt/api/v1/neaps/${id}/test

where,

  • {id} - is the NEAPS ID to be tested

  • the POST request payload takes the following inputs (Refer to the Navigator MC API for the exact schema definition)

    • ncId (string) the mandatory ID of the Network Construct to use with the test audit/fix

    • customProfileData (object) the optional custom profile data if user wants to test the full audit with finding evaluation

    • includeFix (boolean) the optional flag set to true if user wants to test the fix process (default false) after a full audit process with finding

The Navigator MC API for these operations comes with three sample test payloads (based from NTP PN10x):

  • Simple audit test: the ncID is only set to execute the audit process up to the finding evaluation

    • This is useful to quickly and only test the audit process script(s)

    • Also, if the NEAPS has the profile data model defined the captured records include a sample of the profileData that can be re-used as custom profile for subsequent test

  • Full audit test: the ncId and customProfileData are pre-populated

    • This is useful to fully test audit including the finding evaluation (comparison between NE audited data and a given custom profile)

  • audit and fix test: all three inputs are provided

    • fix is only exercised if the prior audit comes up with finding (no match with provided custom profile)

It is recommended to use this test operation after submitting a NEAPS update (PUT) to validate all changes. And, to simplify the NEAPS development cycle, it is recommended to make small changes and immediately test them to simplify any troubleshooting of a test audit/fix failure (e.g. test after add/modify one attribute at a time)

NEAPS Update Validation

To prevent any potential irreversible impact all REST APIs updating an existing NEAPS resource are rejected if:

  • existing custom profile(s) associated with the updated NEAPS exist

  • existing audit(s) associated with the updated NEAPS exist

NEAPS Versioning

  • All NEAPS resources have the default "1.0.0" version assigned to them at creation. See NEAPS MetaData.

  • neFunction value can be used to define a new version of an already supported NE function

    • This approach can be useful to work on the modification of an existing NEAPS with changes that may be impacting existing custom profiles and audits

    • For example, new NEAPS with NTPv2 or NTP V2 can be created to support a modification of the existing NTP

General NEAPS Design Recommendations and Validations

Here are some general recommendations any user should follow when designing a new NEAPS, or making changes to an existing NEAPS:

  • Verify the NEAPS script declarations by doing a manual execution of all the protocol commands

  • Verify proper rendering of the protocol commands using online FreeMarker tools such as https://try.freemarker.apache.org/

  • Verify the NEAPS mapping declarations using:

    • output data samples from protocol command execution

    • Online mapping tools such as:

      • for mapping based on JSON Path (e.g. with TL1 commands): https://jsonpath.com/

      • for mapping based on XML Path (e.g. with NETCONF commands): https://www.freeformatter.com/xpath-tester.html

The validation of new or updated NEAPS should always include these Navigator MC UI steps (note that the same could be done using REST APIs):

  1. Validate the NEAPS generated default profile (Navigator MC UI)

    • find it in the Audit profiles

    • validate that its data model aligns with the NEAPS profile data model declarations

  2. Validate custom profile management

    • verify that Copy of the NEAPS generated default profile is possible

    • verify that the UI editor handling for each defined attributes is as specified by NEAPS

    • confirm the creation of the custom profile

  3. Validate audit of the custom profile

    • verify an audit can be started for selected network elements that match the NEAPS neTypeGroups

    • verify the execution of an audit with:

      • no finding (full match)

      • finding details based on known configuration of the selected network element

  4. Validate fix of an audit with finding reported

    • verify the fix can be started when profile attribute finding is fixable as specified in NEAPS

    • verify the successful fix execution

    • validate the fix by running another audit resulting in no finding found

Design NEAPS with NETCONF commands

This is the step-by-step design guidelines to define the NEAPS resource of an NE Audit profile capability based on the following considerations/requirements:

  • to cover product families (Network Element type groups) that support NETCONF communication protocol such as PN10x

  • audit and fix process flows rely on the use of NETCONF RA Cut Through normalized rules (Rule Engine resources)

NE Audit capability declaration

This is the initial step of the NEAPS design process where the purpose of the new NE Audit profile is established with the goal to set all the NEAPS Core Definitions.

Also, preliminary work is necessary to understand the goals of the new NE Audit profile in terms of:

  • Expected NETCONF protocol commands to be used to audit all profile attributes, and

  • Optionally, identify the corresponding NETCONF protocol commands to be used to fix all auditable profile attributes.

Sample NEAPS core declaration (NTP PN10x)

Below is a snippet of the NTP PN10x NEAPS Core definitions.

{
  "description": "This NEAPS is to support NTP NE Function with NEs managed by NETCONF and PN10x",
  "neFunction": "NTP",
  "neTypeGroups": [
    "PN10x"
  ]
}

Audit process declaration

This step includes the declaration of all the NEAPS processSpecifications definitions that are relevant for the audit process.

  • neProtocol is to use the netconf NE protocol. This is deprecated in release MCP 7.2 or higher (un-used as obsolete by ruleFamily definition)

  • namespaces is set with all NETCONF namespaces expected to be found in the XML commands for audit and fix

  • audit object definitions are set as followed

    • ruleFamily must be set with NeAuditNormalizedNetconf

    • ruleSet must be set with neAudit

    • declare as many scripts as there are NETCONF XML commands that are required to support the audit of this function

      • The role of all audit scripts is by default GET

      • The scope of all audit scripts is by default PER_NODE (can be omitted in NEAPS)

Profile data model declaration

Now that the NEAPS processSpecifications is defined to cover the audit process with the declaration of all the relevant NETCONF commands, the declaration of the NEAPS profile data model definitions can be specified.

  • Declare all the profile attributes based on the NEAPS Profile Definitions

  • The profileAttributeSpecifications is set with the declaration of all root attributes

  • The declaration of all attributes based on array and object schema types include the declaration of the contained/nested profile attributes in nestedProfileAttributeSpecifications

  • Each profile attribute declaration has the auditMapping which is used for the mapping from the NETCONF command response(s). See Audit mapping from NETCONF

At this point, all NEAPS declarations shall be defined for a valid NEAPS to support the audit only based on the designated core definitions.

Audit mapping from NETCONF

The auditMapping NEAPS definition must be set with the XMLPath expression to find the value of the given NEAPS profile attribute in the NETCONF RA Cut Through response. It is set with:

  • an absolute path for all directly addressable elements.

  • a relative path for all elements within a sequence (list/array).

Here is an example of NETCONF XML response based on the audit of the default NTP NEAPS.

<data xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">

    <ntp xmlns="http://www.ciena.com/ns/yang/ciena-ntp">
      <admin-state>enabled</admin-state>
      <mode>polling</mode>
      <polling-interval-min>16</polling-interval-min>
      <polling-interval-max>32</polling-interval-max>
      <authentication>
        <auth-admin-state>disabled</auth-admin-state>
      </authentication>
      <associations>
        <remote-ntp-server>
          <server-entry>
            <address>10.33.80.36</address>
            <admin-state>enabled</admin-state>
          </server-entry>
          <server-entry>
            <address>10.128.8.89</address>
            <admin-state>enabled</admin-state>
          </server-entry>
          <server-entry>
            <address>10.10.10.10</address>
            <admin-state>enabled</admin-state>
          </server-entry>
        </remote-ntp-server>

</data>

The following is a summary of all NTP NEAPS profile attribute auditMapping declarations per attribute name.

  • mode (1) - /netconf:data/sys:system/ntp:ntp/ntp:mode

  • adminState (1) - /netconf:data/sys:system/ntp:ntp/ntp:admin-state

  • pollingIntervalMin (1) - /netconf:data/sys:system/ntp:ntp/ntp:polling-interval-min

  • pollingIntervalMax (1) - /netconf:data/sys:system/ntp:ntp/ntp:polling-interval-max

  • remoteNtpServers (2) - /netconf:data/sys:system/ntp:ntp/ntp:associations/ntp:remote-ntp-server/ntp:server-entry

    • address (3) - ntp:address

    • adminState (3) - ntp:admin-state

Notes:

  1. Simple XML element directly addressable directly mapped to profile attribute name

  2. Complex XML element defining a sequence mapped to profile array

  3. Simple XML element addressable relative to its container (complex element defining the sequence)

Fix process declaration

The declaration of the fix process is optional. As with the audit process declaration, it is defined in the NEAPS processSpecifications definitions under the fix definition.

  • See the Audit process declaration for other common and audit declarations in processSpecifications

  • fix object definitions are set as followed

    • ruleFamily is set with NeAuditNormalizedNetconf

    • ruleSet is set with neFix

    • Declare as many scripts as there are NETCONF XML commands that are required to support the fix of this function

      • Note that these scripts are based on Free Marker templates. See Fix mapping to NETCONF

      • All fix scripts scope is by default PER_NODE (can be omitted in NEAPS)

      • Two types of role are supported:

        • SET for a command that will set the NE Configuration based on the selected custom profile (fix template object). Note that the SET can also be used as template of a delete type NETCONF command. It is all driven-by the template conditional logic.

        • DELETE for the very specific case of a command that handles the explicit deletion of obsolete object(s) from nested list/array

Fix mapping to NETCONF

The fix script FreeMarker template declarations are rendered as true NETCONF XML-base commands using:

  • for SET role, the selected custom profile as JSON object

  • for DELETE role, the deleteObject template variable is set with the list of object ids for all obsolete list objects per list container names. See NTP PN10x NEAPS below.

Note that all FreeMarker variables must be based on the javaName NEAPS definition of the profile attribute as the name is a free (user-friendly) string without characters restrictions such as using space(s).

Here is an example of FreeMarker template of the NETCONF XML request based on the NTP PN10x NEAPS.

<edit-config>
  <target>
    <running/>
  </target>
  <config>
    <system xmlns='http://openconfig.net/yang/system' xmlns:ncx='http://netconfcentral.org/ns/yuma-ncx'>
      <ntp xmlns='http://www.ciena.com/ns/yang/ciena-ntp'>
        <#if adminState?has_content><admin-state>${adminState}</admin-state></#if>
        <#if mode?has_content><mode>${mode}</mode></#if>
        <#if pollingIntervalMin?has_content><polling-interval-min>${pollingIntervalMin}</polling-interval-min></#if>
        <#if pollingIntervalMax?has_content><polling-interval-max>${pollingIntervalMax}</polling-interval-max></#if>
        <#if remoteNtpServers?has_content>
        <associations>
          <remote-ntp-server><#list remoteNtpServers as s><#if s.address?has_content>
            <server-entry>
              <address>${s.address}</address>
              <#if s.adminState?has_content><admin-state>${s.adminState}</admin-state></#if>
            </server-entry></#if></#list>
          </remote-ntp-server>
        </associations></#if>
      </ntp>
    </system>
  </config>
</edit-config>

Design NEAPS with TL1 commands

This is the step-by-step design guidelines to define the NEAPS resource of an NE Audit profile capability based on the following considerations/requirements:

  • to cover product families (Network Element type groups) that support TL1 communication protocol such as Ciena6500

  • audit and fix process flows rely on the use of TL1 RA Cut Through normalized rules (Rule Engine resources)

  • The first step of these rules is about the discovery of all NE (e.g. Ciena6500) shelves. The following variables are then made available to use in all relevant NEAPS definitions:

    • ${shelf} the shelf name

    • ${shelfRole} the shelf role (e.g. primary or member)

  • Expected TL1 protocol commands to be used to audit all profile attributes, and

  • Optionally, identify the corresponding TL1 protocol commands to be used to fix all auditable profile attributes.

Audit process declaration

This step includes the declaration of all the NEAPS processSpecifications definitions that are relevant for the audit process.

  • neProtocol is to use the tl1 NE protocol. This is deprecated in release MCP 7.2 or higher (un-used as obsolete by ruleFamily definition)

  • namespaces is omitted as not used for TL1 messaging

  • audit object definitions is set as followed

    • ruleFamily is set with NeAuditNormalizedTl1

    • ruleSet is set with neAudit

    • declare as many scripts as there are TL1 commands that are required to support the audit of this function using the following script definitions specific to TL1

      • scope the PER_SHELF can be used if all TL1 audit commands are executed against each audit discovered shelf when applicable (e.g. TIDc Ciena6500 NE). Note that mix use of PER_NODE and PER_SHELF is not supported!

      • script is expected to either be:

        • a straight TL1 command if the scope is set with PER_NODE (default) option, or

        • a TL1 command captured as FreeMarker template using the ${shelf} variable to generate a TL1 command for each discovered shelf

      • responseSyntax the expected format of the TL1 response to parse it to a JSON equivalent object See Audit mapping from TL1

Audit mapping from TL1

The mapping of all the audit TL1 commands can be summarized as followed:

  1. parsing from the TL1 response from execution of each TL1 script command to produce a JSON audit object per command

  2. mapping from each command parsed JSON audit object to produce the JSON audit object still per command

  3. merging of all JSON audit objects generated per captured TL1 script command to produce either

    • a single audit JSON object if all audit TL1 scripts are PER_NODE scope, or

    • multiple audit JSON objects for as many discovered NE shelves if all audit TL1 scripts are PER_SHELF scope

Fix process declaration

The declaration of the fix process is optional. As with the audit process declaration, it is defined in the NEAPS processSpecifications definitions under the fix definition. See the description details in NEAPS Process Definitions.

  • See the Audit process declaration for other common and audit declarations in processSpecifications

  • fix object definitions is set as followed

    • ruleFamily is set with NeAuditNormalizedTl1

    • ruleSet is set with neFix

    • Declare as many scripts as there are TL1 commands that are required to support the fix of this function

      • Note that these scripts are based on Free Marker templates. See Fix mapping to TL1

      • As with audit process, all fix scripts scope can either be PER_NODE (default if omitted in NEAPS) or PER_SHELF with the ${shelf} variable to generate a TL1 command for each discovered shelf

      • Note that there is currently no attempt to evaluate all the fix TL1 command responses

Design NEAPS with CLI commands

This is the design guidelines of a NEAPS resource to support audit and fix processes using CLI commands that are executed using the RA Cut Through REST API of the audited NEs.

These guidelines are summarized as followed:

  • Definition of the audit process with CLI commands

  • Definition of the rule processors for the CLI to JSON parsing

  • Definition of the profile attributes mapping from CLI audit output

  • Definition of the fix process with CLI commands

  • Data samples based on TACACS NE function with CienaWaveserver CLI commands

Note that the NEAPS resource neTypeGroups core definition shall be set with the proper NE type group(s) or product family names to ensure:

  • all internally defined CLI commands (audit and fix processes) are only to be used with the defined NE type groups (e.g. set CienaWaveserver as the type group if NEAPS is designed using CienaWaveserver CLI commands)

  • this logical association is maintained between all profiles derived from the given NEAPS and the to-be-audited NEs (e.g. NE Audit UI creation will only allow appropriate NEs to be selected for the selected profile)

Definition of the audit process with CLI commands

First, refer to all NEAPS audit process definitions that are used when defining the specification of an NE function audit process.

For an audit process using CLI commands, the NEAPS audit process definitions shall be set as followed:

  • The ruleFamily must be set with the NeAuditNormalizedCli

  • The ruleSet is set to select the neAudit

  • The scripts array is set with a script object for each CLI command to be executed by the audit process in the defined order. Each script object shall be defined with:

    • The name as the arbitrary but unique audit process operation name,

    • The script as the CLI command.

  • The ruleProcessorKeys is set with the key of the rule processors to be executed as post process of all the audit CLI commands (via the NE RA Cut Through). See next section for details about the rule processor definitions.

See sample of the audit process for TACACS NE function with CienaWaveserver CLI commands.

Definition of the rule processors for the CLI to JSON parsing

The NEAPS process specification can be set with all the necessary rule processor definitions that are used to perform selective parsing to JSON object of some elements of the CLI output captured from running all the audit CLI commands.

The CLI to JSON rule processor shall be used with NEAPS audit process based on CLI commands, which allows the parsing of the following two CLI output patterns as text data tables:

  • Name and value pairs table format. See example below of this table format with 3 name and value pairs.

+--------------- title -----------------+
| Parameter                  |  Value   |
+----------------------------+----------+
| name1                      | value1   |
+----------------------------+----------+
| name2                      | value2   |
| name3                      | value3   |
+----------------------------+----------+

  • Objects table format. See example below of this table format representing two objects with three attributes.

+-------------------------------------------------- title -----------------------------------------------------------+
| Attribute1                              | Attribute2                                  | Attribute3                 |
+-----------------------------------------+---------------------------------------------+----------------------------+
| value1.1                                | value1.2                                    | value1.3                   |
| value2.1                                | value2.2                                    | value2.3                   |
+-----------------------------------------+---------------------------------------------+----------------------------+

Here is the description of these rule processor definitions:

  • key the unique name of the generated JSON object from the CLI parsing

  • type always use the cliToJson constant to select CLI to JSON the rule processor, which must always come with the following name and value pair parameters definitions:

    • key = title and value set with the pattern of the CLI table title

    • key = option and value set with the type of the expected CLI table data format which can be one of the following enumeration

      • nameValueTableWithTitle to select name and value pairs table format

      • objectListTableWithTitle to select objects table format

See sample of some CLI to JSON rule processors to parse output from TACACS NE function CienaWaveserver CLI commands.

Definition of the profile attribute mapping from CLI audit output

The auditMapping definition found in all definitions of the NEAPS resource profile attribute specifications shall be set with the JSONPath expression that allows the selection of the profile attribute value from the CLI audit JSON output.

In this example; tacacsAttributes.['Global servers'].capitalize() the value is selected from:

  • the tacacsAttributes JSON object generated by a defined CLI to JSON rule processor

  • its Global servers object attribute

  • its first letter is capitalized

See samples of profile attribute definitions for TACACS NE function mapped from with CienaWaveserver CLI commands

Definition of the fix process with CLI commands

First, refer to all NEAPS fix process definitions that are used when defining the specification of an NE function fix process.

For a fix process using CLI commands, the NEAPS fix process definitions shall be set as followed:

  • The ruleFamily must be set with the NeAuditNormalizedCli

  • The ruleSet is set to select the neFix

  • The scripts array is set with script objects used to build the ordered list of all CLI commands to be executed by the fix process. Each script object shall be defined with:

    • The name as the arbitrary but unique fix process operation name,

    • The role to identify the operation as SET or DELETE,

    • The script is either a straight ready to use CLI command or the Free Marker template to generate CLI command(s).

  • See sample of the audit process for TACACS NE function with CienaWaveserver CLI commands.

  • See details below for specific definitions of the two supported fix operation roles.

SET fix script

The SET role is used for most fix process CLI commands.

It can be a constant CLI command such as the configuration save to commit all changes associated with all previously executed CLI commands.

But it is most of the time set as a Free Marker template to generate:

  • one CLI command, or

  • an array of CLI commands in this format; ["command1","command2"]

The template variables are as followed:

  • the fixObject represents the selected audit profile as JSON object

  • each profile attribute is accessed using its javaName as defined in the NEAPS profile attribute definition

Here is an example of s script to generate one CLI command:

  • script definition; <#if (fixObject.state)??>tacacs <#if fixObject.state == 'Enabled'>enable<#else>disable</#if></#if>

  • generates the CLI command; tacacs enable

  • with audit profile attribute state set with Enabled value.

This is an example of a script to generate multiple CLI commands:

  • script definition; <#if (fixObject.globalServersList)??>[<#list fixObject.globalServersList as globalServer>\"tacacs add server ${globalServer.hostname}<#if (globalServer.priority)??> priority ${globalServer.priority}</#if><#if (globalServer.port)??> tcp-port ${globalServer.port}</#if><#if (globalServer.secret)??> secret ${globalServer.secret}</#if>\"<#if (globalServer.state)??>,\"tacacs <#if globalServer.state == 'Enabled'>enable<#else>disable</#if> server ${globalServer.hostname}\"</#if><#sep>,</#list>]</#if>

  • generates the CLI command; ["tacacs add server global1 priority 5 port 49","tacacs enable global1","tacacs add server global2 priority 5 port 49","tacacs enable global2"]

  • with audit profile attribute array globalServer that is set with two objects populated with priority and port defined values.

The execution order of all the SET CLI commands:

  • as captured in the fix scripts array definition

  • all SET CLI commands are executed after the DELETE CLI commands

  • again, reminder that the last CLI command should be configuration save

DELETE fix script

The DELETE role is reserved for the handling of the profile attributes based on an array of objects.

To ensure that the NE configuration is strictly configured from the audit profile, the management of these profile attribute arrays in terms of CLI commands is always carried out in two steps:

  1. DELETE all existing objects/items found during the audit process prior to this fix process (fix is always subsequent operation associated with audit findings)

  2. SET all objects/items as defined in the audit profile

So, this role is used for the generation of all the CLI commands for the first step above, which is to cover the deletion/removal of any existing NE configuration.

The specific script definitions with the DELETE role are as followed:

  • the script template must use the itemId variable to generate the delete CLI command for each profile array item currently configured on the NE

  • the following parameter must be set to associate the delete CLI command with the profile attribute array

    • key set with arrayName

    • value set with the name of the profile attribute array

Finally, the execution order of all the DELETE CLI commands is:

  • based on the order they are defined in the NEAPS fix scripts definition

  • carried out before the sequence of all SET CLI commands (see SET CLI commands above)

Design NEAPS with NE data access using Navigator MC REST GET API

The following section details general guidelines for designing a NEAPS resource for auditing NE data. Assuming that NE data is retrieved via GET REST API of a Navigator MC microservice.

Note that fix process specification is not supported.

All samples below are snippets from the default NEAPS for PON(OLT) function and PN10x type group that is designed based on this normalized set of rules.

Sample Audit Process Specification

See below the sample audit process specification to search for all NSI entity OLT equipment entities followed by the description of all of its definitions.

{
  "processSpecifications": {
    "audit": {
      "ruleFamily": "NeAuditNormalizedMcpRest",
      "ruleSet": "neAudit",
      "scripts": [
        {
          "name": "getAllOltEquipments",
          "role": "GET",
          "script": "/nsi/api/search/equipment?searchType=wildCard&networkConstruct.id=${ncId}&cardType=SFPplus-OLT&limit=1000&metaLimit=0&safeLimit=false",
          "scope": "OLT",
          "parameters": [
            {
              "key": "neConfigNameJsonPath",
              "value": "attributes.locations[0].oltName"
            },
            {
              "key": "neConfigDisplayNameJsonPath",
              "value": "attributes.displayData.displayName"
            }
          ]
        }
      ]
    }
  }
}

  • ruleFamily and ruleSet are the references to the normalized rules that allow audit based on Navigator MC REST GET API.

  • name this is the arbitrary name of the REST GET operation

  • script this is the REST GET API endpoint template (expecting the use of the ${ncId} template variable)

  • scope this is the mandatory word used to identify the entity type retrieved from the REST GET response

  • neConfigNameJsonPath mandatory JSONPath expression parameter to select the (native) name of the audited entity

  • neConfigDisplayNameJsonPath mandatory JSONPath expression parameter to select the display name of the audited entity (used in audit finding)

Sample Audit Process Specification

See below the sample of an audit profile attribute specification that includes the auditMapping definition as the JSONPath expression to select the profile attribute value from the selected audit entity from the REST GET response.

{

NEAPS Troubleshooting

The purpose of this section is to help resolve the difficult (non-trivial) issues found during:

  • the management of NEAPS. See NEAPS REST APIs

    • A Bad/Invalid request error is always associated with an JSON issue. See REST POST/PUT Bad Request - Unable to process JSON

    • An Internal system error may have impacted the management of the NEAPS associated resources. See NEAPS Associated Resources

  • the audit or fix process of a custom audit profile associated with the NEAPS

    • This troubleshooting guideline only applies to audit profiles associated with NEAPS. See Commissioning Profiles and Capability

    • Many defects in NEAPS declarations may be caught during these NE Audit processes. See NEAPS Impacting Audit/fix Processing Errors

REST POST/PUT Bad Request - Unable to process JSON

Reason

The NEAPS JSON object found in the request message of the POST or PUT operation is invalid for the possible reasons:

  1. the JSON object is invalid/malformed

  2. fails to validate with JSON schema (NEAPS resource definitions).

Find in the Navigator MC System Logs for the configmgmt app the log associated with the reported HTTP error. An easy way to find the log is:

NEAPS Impacting Audit/fix Processing Errors

Most audit or fix processing errors of a relevant NEAPS associated profile (See Commissioning Profiles and Capability) may come from incorrect NEAPS declaration(s).

The reporting of these processing errors is very likely associated with a RuleEngine failure to execute an audit or fix processing rule from the profile associated NEAPS. See NEAPS Audit/Fix Processing Errors for some examples of NEAPS processing rule reporting cases.

Troubleshooting should start by looking for the Navigator MC System Logs to get the reason and all possible details that caused the failure. See NEAPS Rules Exception Log Data.

Finally, always try to follow these Basic NEAPS Design Recommendations and Validations to validate al NEAPS declarations as early as possible.
