Performance monitoring

The Performance Metrics or Performance Monitoring (PM) microservice orchestrates the collection of metrics from resources.

When resources are added to the system, the microservice detects and determines their capabilities with respect to collection intervals and available data resolution. A collection schedule for the resource is created and started.

The microservice offers a REST API to change collection schedules for individual resources or resource types.

Configuration

PM configuration is driven by the Global Configuration Service (GCS). All configuration options, listed below, can be changed at runtime using the GCS REST API.

NOTE : It may require restarting the PM microservice for certain configuration changes to take effect. Please read the description carefully.

The following request will update all PM instances that are active to true.

curl -X PUT "https://10.186.0.150/gcs/api/v1/config" -H "accept: application/json" -H "Authorization: Bearer f26496bb422d3c120cea" -H "Content-Type: application/json" -d '[ { "application": "pm", "instance": "-", "partition": "hpm", "name": "active", "value": "true" }]'

Filter 6500 HPMs

Currently, port stats, sub-port stats, Y1731 (dmm/slm/mef_slm/mef_dmm) stats, Qgroup stats, and RSVP stats are all being fetched by default. ip_dmm,ip_slm,ip_mef_dmm,ip_mef_slm will also be supported now.

If a user wants to filter stats then he can update the below GCS property with values which would be from the pre-defined value set mentioned in the description.

GCS Property to filter 6500 HPMs

{

    title='HPM Filters',
    description='HPMs will be filtered on basis of values provided from defined value set (rsvp_in_lsp, port, '
                'subport, q_group, dmm, slm, mef_slm, mef_dmm, ip_dmm, ip_slm, ip_mef_dmm, ip_mef_slm)',
    key='pmFilters',
    default='rsvp_in_lsp, port, subport, q_group, dmm, slm, mef_slm, mef_dmm,  ip_dmm, ip_slm, ip_mef_dmm, ip_mef_slm'

}

Limitations

  • The value of GCS property would not be validated i.e., the user has to be cautious while defining the values.

  • GCS property is a simple string value which can not be validated. Even if we try to validate it at Navigator MC it won`t have any impact since it will fail the entire PM call seamlessly and the user will never know.

  • Filter values can not be other than defined values. It can be a subset though.

  • Incorrect values will be ignored and if all values are incorrect then no stats will be published.

  • ip related filters(ip_dmm, ip_slm, ip_mef_slm, ip_mef_dmm) have been added MCP8.0 onwards.

Query real-time PMs

To query real-time performance metrics (PMs), use the Performance metrics API.

To query historical PMs, see Query historical PMs.

Requirements

Ensure the following:

  • You have an API token (see Obtain an API token).

  • You have the NE Session ID.

  • You have the resourceID (Network Construct identifier), (obtained by querying the TPE using the NCID [through {NAVIGATOR_MC_HOST}/nsi/api/vi/tpes?ncid=<NCID>]).

  • You have the TIDs and NCIDs for the enrolled ROADMs.

  • You have populated the resourceObject by applying the various fields from the TPE data. For example, resourceObject.location can be populated with the data from the TPE attributes.location field.

If you are specifying the "nativePmFacilityName" in the resourceObject, keep in mind that the format is device-specific.

For 6500 these formats can be quite complicated. For example, for RTRV-PM-ODUTTP for 6500 12.6:

  • The general format is:

    ODUTTP-shelf-slot-port-rt1Ptp1-rt2Ptp2-rt3Ptp3-rt4Ptp4

  • Example ranges for a 32-slot shelf are:

    ODUTTP-[0..992]-[1..8,11..18,21..28,31..38]-[1..42,100..110]-[4,C2,C4,CN]P[1]-[3,3E2,4,C2,C4,CN]P[1..80]-[2,2E,3,4]P[1..32]-[1]P[1..8]

When formulating PM queries, refer to the relevant RTRV-PM-* command in the TL-1 command definition.

  • Identify the following:

    • granularity: UNTIMED, 15_MINUTE, 24_HOUR, BASELINE, ALL

    • binIndex (optional): This option specifies the bin number of a range of bins. The default is 0, and the format is 0 | 0,1-3,5-7,21 | 0-32 | 1,3,5,7,9.

    • parameters: This is a list of strings identifying the native PM name (for example, OPR-OTS, OPRMAX-OTS).

54xx specific behavior

Special PM collection behaviors specific to 54xx include the following:

  • “bin index” filtration is not supported and 54xx RA will always collect real time PM from current bin (which is bin index “0”). Any range given ( e.g. 0,1-3,5-7,21 | 0-32 |1,3,5,7,9) will be ignored and only current bin (which is bin index “0”) will be retrieved and returned.

  • "suppress" filtration is not supported as 54xx device does not support to suppress any data.

  • “parameter” filtration is not supported.

  • "location" based retrieval is not supported and resourceObject in retrieval request should contain valid "nativePmFacilityName" for a given facility.

Guidelines to tune PM instances and its related configurations

If historical performance metrics APIs are unable to provide the complete data set of HPM, then it may be a case wherein continuous lags are building upon the kafka topic and ingestion of data is not matching the speed of data generation. In such cases, GCS configurations are exposed which need tuning along with increasing PM instances if required.

Requirements

Ensure the following:

  • In case L0 NEs of type RLS and 6500 are managed on the cluster and lags are continuously increasing then

    • On the 5+1 cluster, change scale the pm instances from default 6 to 12 and the PM collection worker-thread from default 50 to 25.

    • On the 4+1 cluster, change scale the pm instances from default 4 to 12, and the worker-thread from default 50 to 17 and so on.

      For adjusting the worker threads, GCS config ‘Collection Workers’ should be used. Make sure to restart the PM service if it is scaled up.

Query historical PMs

To query historical performance metrics (PMs), use the Performance metrics APIs.

The HPM query APIs have evolved from v1 to v2, and then from v2 to v3. Paging support was added in the v2 HPM query API, and cursor-based paging support was added to the v3 API so that only tags with matching data points are returned in the query response.

To query real-time PMs, see Query real-time PMs.

Requirements

Ensure the following:

  • You have an API token (see Obtain an API token).

  • You have the TIDs or NE display names for the enrolled ROADMs to filter based on NE.

  • Identify the following to define a time range for HPM collection, absolute or relative:

    • To define an absolute time range:

      • define "startTime" to be the date and time of the earliest PMs to be collected in the Coordinated Universal Time (UTC) format ‘YYYY-MM-ddTHH:mm:ss.SSSZ’.

      • define the "interval" with units of minutes('m'), hours('h') or days('d') for the time range.

      • alternatively, define explicit "endTime" to be the date and time of the latest PMs to be collected in the Coordinated Universal Time (UTC) format (YYYY-MM-ddTHH:mm:ss.SSSZ).

        The start time must precede the end time.

    • To define a time range relative to the current time:

      • define a value and its unit of the time to wind back.

        Supported units are months('MONTHS'), weeks('WEEKS'), days('DAYS'), hours('HOURS'), minutes('MINUTES'), seconds('SECONDS') and milli-seconds('MILLISECONDS').

      • you can specify the time range with an explicit interval value.

      • if you do not specify an interval, the time range extends to the current time.

  • HPM query results can be filtered on one or more tags.

    • granularity: the filter granularity is based on PM collection granularity (UNTIMED, 15_MINUTE, 24_HOUR, BASELINE, ALL).

    • "parameterNative": This is a list of strings identifying the native PM name (for example, OPR-OTS, OPRMAX-OTS).

  • HPM query results can be sorted on one or more than one tag:

    • by default, query results are sorted in ascending order.

    • if you precede the sorting tag name with a dash, query results will be sorted in descending order.

OSS metrics query API guidelines

To query OSS metrics (PMs), use the /pm/api/v1/query/ossMetrics API.

Requirements

Ensure the following:

  • You have an API token (see Obtain an API token).

  • Consider using some or all of the following fields in order to make efficient PM queries.

    • NE Name (networkElementName)

    • Parameter Name (parameterNative)

    • Measurement points (facilityNameNative)

  • Always use granularity to make the query more efficient.

  • Wherever possible, use Parameter and NE name (or a list of names) together to make the query more efficient.

  • In case the number of enrolled NEs is large, then build an OSS query as per the following rules:

    • Prefer to use “equal” in the query. It is not recommended to use “contains”, “startWith”, “endWith” in the queries.

    • Never build a query to fetch PM data for all NEs and all parameters. If required, then break the query into smaller sets of NEs and parameters.

    • Break the OSS queries in such a way that the returned response should not be huge (A memory limit of 12 GiB is defined for Clickhouse queries).

    • The combination of NE names and parameter names may need to be tuned in order to limit the memory usage and reduce pagination.

    • If specifying a list of parameter names, limit it to 10.

  • PM API calls must be executed sequentially.

  • Because the data is stored in time series, lower frequency queries for longer time periods are more efficient. Don’t execute sets of queries less frequently than once every two hours.

  • Maintain at least 2-second gap in each subsequent paginated query.

  • Does not support sort order

  • Keep the limit of page size between 200K to 400K

  • Time range could be absolute or relative

  • Only the below parameters will be available in the tags sections of the response. If more tag details needed, Please use metrics API. More detail is added(here OSS query API guidelines for historical PMs)

    • granularity

    • parameterNative

    • networkElementName

    • location

    • direction

    • facilityNameNative

    • aggregateNE

    • aggregatedLocation

    • pmResourceId

        "and",
        [
          "=",
          "parameterNative",
          "OPTMAX-OCH"
        ],

          "=",
          "granularity",
          "15_MINUTE"
        ]
      ],
      "pageSize": 400000,
      "range": {
        "type": "relative",
        "unit": "HOURS",
        "Value": 2
      },
      "tags": [
        "networkElementName",
        "parameter",
        "facilityNameNative"
      ]
    }
  }
}

    • Break the OSS queries in such a way that the returned response should not be huge (A memory limit of 12 GiB is defined for Clickhouse queries).

    • The combination of NE names and parameter names may need to be tuned in order to limit the memory usage.

    • If specifying a list of parameter names, limit it to 10.

  • PM API calls must be executed sequentially.

  • Because the data is stored in time series, lower frequency queries for longer time periods are more efficient. Don’t execute sets of queries more frequently than once every two hours.

  • Maintain 5 seconds gap between every two queries and 2 seconds gap in each subsequent paginated query.

  • Queries will be more efficient if you do not specify a sort order.

  • Keep the limit of page size to default 10000.

    For GR deployments: Since large queries can use a significant amount of system resources, it is recommended that queries be executed on the standby site.

Threshold endpoints

A threshold consists of the following:

  • "name": any string to use as a human-readable identifier.

  • "thresholdType": the type of threshold, either "max", "min", or "deviation".

  • "value object": the value, if crossed, triggers the action. Must correspond to the thresholdType (see example below).

  • "pmParameter": the PM parameter to be monitored.

  • "tags": the specific metric tags to be matched. All tag values specified here must match for a positive match.

    • Currently only "granularityNative" is supported in exact match. This is the bin time, if applicable (for example, 15-MIN); if not specified, PM granularity will be ignored

    • Threshold v3 endpoint introduced below changes:

      • API /v3/thresholds accept granularity instead of granularityNative in the tags attribute

      • The valid granularity values are 5_MINUTE, 15_MINUTE, etc. or 24_HOUR; if not specified, the PM granularity check will be ignored.

  • "action object": the action that is triggered upon crossing the threshold.

    • Currently only "alarmAlert" is supported (see example below) with "severity" values of INDETERMINATE, CRITICAL, MAJOR, MINOR, WARNING, INFO, CONFIG, or DEBUG.

Historical statistics collection and retrieval for Y.1731/MEF35.1 mode

The historical statistics collection and retrieval provide the following parameters:

  • User can filter specific statistics on basis of facilityNameNative and tags, while fetching statistics from PM database.

  • To avoid performance issues during Historical performance monitor (HPM) collection and duplicity of data, MEF statistics are not collected in case granularity per 24 hours.

  • The collection interval is less than 15 minutes.

  • PM collection for 6500 devices over the customer’s network is disabled.

Navigator MC supports the configuration of Y1731 stats using remote-mep-id only. MAC configuration is not yet supported.

In case there is any y1731 session configured manually using remote MAC (directly on the Node) it may cause a failure in PM statistics collection at Navigator MC.

MCP 3.6 introduces the Tags [profileType, binNumber] for PM to filter the specific type of statistics:

profileType>> to filter on basis of profileType provided in cfmServiceName assuming that serviceName format will be vsName==profileType

The facilityNameNative syntax remains unchanged. MCP 3.6 uses the existing format for cfm statistics.

facilityNameNative format:-

resourceId::service-name::lmep::rmep::testId

cfm mef synthetic-loss availability show service <name> local-mepid <mepId> session-id <sessionId> history
