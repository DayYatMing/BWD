On-demand reporting

You can generate a report immediately using the Reporting API’s report v1 or v2 calls.

You can generate reports using the Swagger interface that is included with the Navigator MC UI. You must have valid Navigator MC login credentials to access the Swagger UI in Navigator MC.

To run reports from the Swagger UI, navigate to the list of report APIs as described below, and run any single call using its "Try it out" button. Navigator MC will submit the call to the server and display the response to the submitted call in the same UI window. You can copy and paste this displayed information into another application.

To access Swagger:

  1. Log into Navigator MC with your credentials.

  2. Click System > APIs

  3. Click the Reporting entry in the left-hand column.

  4. To view a list of available report types, do the following:

    1. Click the GET /reporting/api/v2/report/supported/reporttype call.

    2. Click the Execute button.

      The Response Body lists the available report types in the current release. Note the string after "reportType", which you will need to generate that report from the API.

  5. To generate a new report, do the following:

    1. Click the POST /reporting/api/v2/report call.

    2. Click the Try it out button.

    3. In the body of the call, replace the text "string" in the following line:

      '"reportType": "string"'

      with the correct reportType string (for example, PW_CIR_REPORT".

      The correct reportType strings for all available report types were displayed in response to the previous call.

  6. Click the Execute button.

Deleting reports

You can delete individual reports using the following API call:

/reporting/api/v2/report/delete/{resourceId}

Use syntax resembling the following:

/reporting/api/v2/report/delete/ece539710ba64937b30b27d6e8e5fc01

Or, you can delete a set of reports that fall within a time range using the same API call, but with syntax resembling the following:

/reporting/api/v2/report/delete?fromDate=2018-02-18T03%3A00%3A17.103Z&toDate=2018-02-19T03%3A00%3A17.103Z&reportType=ETHERNET_LINKS_REPORT

Working with report schedules

To create and manage a schedule that will cause the automatic generation of a report, use the Reporting API’s Schedule calls.

The payload required for the API call (/reporting/api/v2/schedule/create) is:

{
        "cronExpression": "string",
        "cronExpressionFormat": "string",
        "reportType": "string"
}

Where:

  • cronExpression: You can provide cron expression for the schedule and reporting server will take care of repetitive occurrence of the schedule.

  • cronExpressionFormat: You must provide the cron expression format. Acceptable values are "QUARTZ" or "UNIX".

  • reportType: This is the type of report you are scheduling.

Sample Response:

{
    "data": [
         {
          "id": "ddbad61a1eb544e98bb7b829a034aef7",
              "type": "reportingSchedule",
              "attributes": {
                  "resourceId": "ddbad61a1eb544e98bb7b829a034aef7",
                  "reportType": "ETHERNET_LINKS_REPORT",
                  "cronExpression": "00 00 19 23 May ? 2018",
                  "cronExpressionFormat": "QUARTZ",
                  "cronDescription": "at 19:00 at 23 day at May month at 2018 year"
           }
         }
     ],
  "links": {},
  "meta": {}
 }

The resourceId uniquely identifies this report schedule. You can use that ID to obtain information about the report, or to delete the report, using the following API calls respectively:

  • GET /reporting/api/v2/schedule/{resourceId} to obtain information about the schedule

  • DELETE /reporting/api/v2/schedule/delete/{resourceId} to delete the schedule

To retrieve a list of all current schedules, use the following call:

  • GET /reporting/api/v2/schedule

The system returns a list of all schedules, each with an associated resourceId.

You can use those resourceId values to retrieve or delete a specific schedule.

Configuring the report retention period using the REST API

You can use the Navigator MC REST API to add a new key-value pair for a custom report type which can have a different retention period from other custom report types. At 00:00 hours each day, Navigator MC automatically deletes reports that have an age that is older than the configured report retention period.

The config module uses the following API call to configure the retention period for each report type:

Request format

POST {NAVIGATOR_MC_HOST}/gcs/api/v1/config

Specify the attributes as follows.

[
  {
    "application": "reporting",
    "instance": "-",
    "partition": "retentionPolicy",
    "name": "desired_name",
    "title": "desired_title",
    "description": "desired_description",
    "value": "desired_value"
  }
]

A list of parameters and related descriptions follows.

Table 1. Parameters and description
Parameter Description

Application

The name of the application for which the “value” parameter is being defined and which is to appear in the Application column of the Configuration window (System > Configuration) of the Navigator MC UI. The value should be "reporting" always in case of the Reporting microservice.

Instance

The name of the instance in the case of a multi-host environment. The value should be "-" always in case of the Reporting microservice.

Partition

The partition of configurations within the Reporting microservice. The value should be "retentionPolicy" always when defining the configuration with respect to reports purging in the Reporting microservice.

Name

The name that displays in the Key column of the Configuration window. This should be same as the custom report type that displays in the Reporting UI.

Title

The title that displays in the Name column of the Configuration window and can consist of any string.

Description

The description that displays in the Description column of the Configuration window and can consist of any string.

Value

The value that displays in the Value column of the Configuration window and should be the number of days to retain this custom report type.

Sample request

{
    "application": "reporting",
    "instance": "-",
    "partition": "retentionPolicy",
    "name": "CUSTOM_TEST_1",
    "title": "Custom Title",
    "description": "Custom description",
    "value": "100"
  }
]

Sample response (for above sample request)

[
  {
    "application": "reporting",
    "instance": "-",
    "partition": "retentionPolicy",
    "name": "CUSTOM_TEST_1",
    "title": "Custom Title",
    "description": "Custom description",
    "value": "100",
    "callbacks": [
      "http://172.16.0.40:8080/configuration/api/v1/callback"
    ],
    "key": "reporting/-/retentionPolicy/CUSTOM_TEST_1"
  }
]

You can also verify that the request is successful by checking that a new row appears in the Configuration window (System > Configuration) of the Navigator MC UI.

Configuring the server details for SFTP transfer of reports using the REST API

SFTP server details can be configured in the Navigator MC to enable the transfer of reports to an external server. Any report generated after configuring the SFTP details will be automatically transferred to the SFTP server. sftpTransferStatus attribute in reportsinfo API can be used to know the status of SFTP transfer, it can have below values -

  • Not configured - When the SFTP details are not configured on the system.

  • Waiting for report - When the report is being generated. Once the report is generated it will be saved temporarily on the disk to make it ready for SFTP file transfer.

  • Transfer successful - When the SFTP transfer is successful.

  • Transfer Failed - When the SFTP transfer is failed due to wrong SFTP details or the SFTP server is not reachable.

Below API can be used to set SFTP details in Navigator MC. Navigator MC users must have an Application admin role to execute this API.

PUT {NAVIGATOR_MC_HOST}/reporting/api/v2/report/setSftpTransferDetails

List of request parameters and its descriptions are as follows.

Table 2. Parameters and description
Parameter Description

serverNameOrIp

Fully qualified domain name or IP of the SFTP server to which reports will be transferred.

port

The port on which SFTP is running. Generally, it runs on 22.

username

A user account on the SFTP server. root user might have restrictions so a non-root user is preferred.

directoryPath

Complete directory path on SFTP server to which reports will be transferred.

authenticationMode

Authentication mode used to login to SFTP server. Valid values are PASSWORD or KEY. If authenticationMode is given as PASSWORD, then login password should be provided through password parameter. If authenticationMode is given as KEY then follow the below steps and use sudo to run commands -

  • Generate RSA public/private key pair through linux command ssh-keygen -t rsa.

  • Copy private key to folder /etc/bp2/authkeys/reporting with the filename id_rsa on Navigator MC host 0.

  • Add public key to SFTP server using ssh-copy-id linux command for all hosts on Navigator MC. The public key can be added manually also.

  • In case of a multi-host environment, synchronize all sites by running bp2-site sync-site-config

password

the password of the given user account if authenticationMode is PASSWORD. If authenticationMode is KEY, then this parameter should not be sent in the request.

Sample request

{
  "serverNameOrIp": "sftpServer123.ciena.com",
  "port": 22,
  "username": "user123",
  "password": "123",
  "directoryPath": "/tmp/reports/",
  "authenticationMode": "PASSWORD"
}
If authenticationMode is given as KEY, be sure that after adding keys to the SFTP server, the server should be reachable via ssh without asking for a password.
Troubleshooting tip: If authenticationMode is given as KEY, and "invalid key" is seen in logs after following the above mentioned steps, may be this is due to the key format provided is unsupported by the third-party library (JSch). Use ssh-keygen command with -m switch to convert the private key format to the RSA or pem mode. For example: If you have OPENSSH key pair which is not supported, then you can convert the private key format to the RSA or pem mode using command ssh-keygen -p -f /etc/bp2/authkeys/reporting/id_rsa -m pem

User can delete the configuration detail saved in the Navigator MC by executing below API DELETE {NAVIGATOR_MC_HOST}/reporting/api/v2/report/delete/sftpTransferDetails

Limitations of Navigator MC UI aligned reports

Equipment not carrying traffic report

The reporting module allows generating a report which will identify equipments that are not carrying traffic. An equipment is not carrying traffic if all client services on the equipment has the 24 hour port utilization less than or equal to the configurable threshold, and a complete data set. Additionally, an equipment must have at least 1 client service to be identifiable.

This report is only available with the Navigator MC Plus license activated
Equipment that contains a Transport Client service with an unsupported layer rate, or a supported service lacking 24 hour port utilization data is not classified as not carrying traffic.

Configuration

There are 2 GCS parameters which allows configuring the threshold for which a service is considered not carrying traffic. Default value is 0.

  1. EthernetOrLAGServiceNotCarryingTrafficThresholdPercent

  2. TransportClientServiceNotCarryingTrafficThresholdPercent

Limitations

  • Supported devices are 6500, Waveserver 5, and Waveserver Ai

  • Supported service types are Transport Client, Ethernet, and LAG, with layer rates DSR_ETHERNET, ETHERNET, or LAG

  • 1+1 TPT and Client OPS services are not supported in MCP 8.0

  • The report is reliant on port utilization data that is a day old. Consequently, there may be instances where equipment is classified as not carrying traffic, but is in fact carrying traffic after the report has been generated. Refer to the Service Utilization documentation for more information

  • The report can inaccurately classify equipment as not carrying traffic if it has a service that is down for a period of 24 hours or more

Creating custom reports

You can create a custom Report Type using Reporting API. Once created, this new Report Type can be used further for report generation, both on demand and scheduled.

The following are the parameters required for this API:

  • reportType - name of the new custom Report Type which you want to create

  • Description - short description of the new Report Type that being created

  • uploadWorkflow - XML file that defines the workflow for the report generation

  • joltFile - JOLT transformation file in JSON format to transform REST API response defined in <url> tag under <mainresource> in uploadWorkflow file.

The following table describes the data in XML file.

Data Description

<?xml version="1.0" encoding="UTF-8"?>

Optional. If XML declaration is not provided, the default will be used

<report>

Mandatory. This is used to define start of new report type workflow.

<mainresource>

Mandatory. This will be used to mark the main REST resource on which the report will be based.

<mainresource> section

<mainresource> section is mandatory. This defines the REST API from which data for the report will be fetched. The JOLT transformation file provided will be used to transform response from this API.

url value: mandatory. URL for REST resource from which data for report will be fetched. Any query parameters whose value need to be replaced, should be written between curly braces: {}.

  • <param> tag is optional. It should be provided only if there are query parameters in the URL.

    • name attribute is used to define the parameter name as is used in the REST API.

    • isoffset attribute is used to mark the parameter to be used as offset when result is fetched in pages. It can have value true/false. If this attribute is not present, then false will be taken as default value.

    • ispagesize attribute is used to mark the parameter to be used to define page-size when result is fetched in pages. It can have value true/false. If this attribute is not present, then false will be taken as default value.

<joltspec> The JOLT Transformation spec to transform the API response should be defined here. The spec should go under CDATA section.

<targetmicroservice>: mandatory. This is used to define the target microservice.

<mapper>: mandatory. This defines what parameters will be in the report’s CSV or JSON file. It can have multiple <param> tags but at least one <param> tag is mandatory.

  • name attribute will be the title of the column in the exported CSV format and will be the attribute-name in JSON format

  • map attribute should be the attribute name from JSON. The attribute value from JSON will become the column value.

<otherresources> section

Optional. <resource> defined in <otherresources> tag will be used to get additional data for report from other REST APIs.

resource: optional. Each <resource> section under <otherresources> describes one REST API to fetch additional data for report generation.

  • url value: mandatory. URL for REST resource from which data for report will be fetched. Any query parameters whose value need to be replaced, should be written between curly braces: {}.

    • <param> tag is optional. It should be provided only if there are query parameters in the URL.

  • targetmicroservice: mandatory. This is used to define the target microservice

  • processinglogic: mandatory. This section defines what logic should be applied to this REST resource’s response to include this in the final report. It should have at least one <add> or <replace> tag. It can have any numbers of <add> and <replace> tags.

    • <add> tag will be used to pick values from this REST resource’s response and will be added in main REST APIs response defined in <mainresource> tag.

      • mappingfield - jsonpath expression to find value from REST response.

      • field - A field/attribute/key will be replaced in final report’s output whose value will be exported in JSON or CSV format.

      • mappingfieldsource - this attribute can be used to tell from where the mappingfield jsonpath expression should be applied. It can have one of the two values mainresource or currentresource

      • <jsonpath> - jsonpath expression that must pick unique value from this REST resource’s response. The value of jsonpath expression defined in mappingfield will be used in jsonpath.

    • <replace> tag will be used to pick values from this REST resource’s response and will be replaced in main REST APIs response defined in <mainresource> tag

      • jsonpath - jsonpath expression that must pick unique value from this REST resource’s response. Any field’s whose value will be replaced must be specified between # as is shown in this sample.

      • mappingfield - name of the field in REST resource’s response whose value will be replaced in jsonpath expression.

      • field - A field/attribute/key will be replaced in final report’s output whose value can be used in report’s output in JSON or CSV format.

Configure socket timeout value in GCS

A socket timeout is a designated amount of time from when the socket connects until the connection breaks. A socket timeout stops this connection after a specified amount of time. The default value for socket timeout is set as 5 in GCS.

A SocketTimeout exception can occur for large scale systems if it takes more than the specified time defined in GCS to get a response from other microservices, and your request expires before getting the response. To avoid this exception, the socket timeout value can be increased in GCS.

Steps for configuring the socket timeout value in GCS

  1. From the top menu bar, Go to System > Configuration

  2. Search for key SOCKET_TIMEOUT on the left side “Refine by” section.

  3. Select the key, and click on the EDIT button.

  4. An “Edit configuration setting” dialog will open, and enter the new value in the input field corresponding to the Value label.

  5. Click on the Save button.
