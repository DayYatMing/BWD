Configurable SRLG format

SRLGs can use any format that includes numbers or strings of printable characters.

MPLS customers use SRLGs which are 32-bit numbers. These SRLGs are restrictive because they must signal the SLRGs around the network and we want to minimize signalling overhead.

Navigator MC (as an SDN controller) is not as restrictive. Navigator MC also accepts long alpha-numeric strings.

Opaque versus structured SRLGs

Opaque SRLGs are values that Navigator MC cannot interpret. These values are provided by you, the customer, and are used by Navigator MC (and/or in-skin controllers like MPLS or OSRP) to create diverse routes. Fully diverse routes have no SRLGs in common. Best Effort diverse routes have some form of minimal intersection. Without being able to interpret SRLGs, the Navigator MC calculation for best effort only minimizes the intersection by the number of SRLGs and not by the importance of individual SRLGs.

Structured SRLGs are made up of fields that provide additional semantics to the value, such as the type of resource that is described by the Subnetwork or RegionId, the riskType that associates a SRLG category, and a riskValue. These fields are then combined to create one SRLG value (by "or’ing" bits into a number or concatenating characters into a string).

Structured SRLG configurable format

The SRLG configurable format includes the following characteristics:

  • Navigator MC ships a default format with the installation.

  • The SRLG format is disabled by default.

  • Once the SRLG format is enabled, the format cannot be changed or disabled. A feature to force update of the SRLG format is available.

  • Navigator MC only allows one SRLG format per deployment.

  • Irrespective of the SRLG format, Navigator MC stores the SRLG internally as a decimal and pushes the same to the network.

  • Navigator MC supports the following fields in the Structured SRLG format:

    • riskType

    • subNetwork

    • riskValue

The SRLG configurable format includes the following configurable attributes:

  • SRLG format type (Opaque or Structured)

  • SRLG display format (Bit, Decimal, Hexadecimal or String - for Opaque format only)

  • Field display names (for example, Subnetwork can be named Region)

  • The start position and length of each field.

The following fields are available to the structured SRLG:

  • The riskType of resource with which the SRLG is associated.

    • The riskType must be pre-defined for auto-assigned SRLGs.

    • Ensure that riskType names are unique.

    • Navigator MC does not validate riskType deletion even if the riskType is associated with a SRLG.

    • Navigator MC ships with the default riskType Mapping. Mapping definitions can be changed using the POST or DELETE nsi/srlgformat/formatmappings API to modify riskType mappings.

To create new Subnetwork mappings, use the SRLGFormat API for format mappings:

POST {NAVIGATOR_MC_HOST}/nsi/api/srlgformat/srlgFormatMappings

Sample request

A response code of 200 indicates that the request succeeded. Upon creating the mappings, these will start appearing as part of the GET nsi/srlgformat and GET nsi/srlgformat/srlgFormatMappings response.

{

      "attributes": {
        "name": "NewSubnetwork2Region",
        "value": "13"
      }
    }
  ]

To delete any obsolete Subnetwork mapping, use the SRLGFormat API for format mappings:

DELETE {NAVIGATOR_MC_HOST}/nsi/api/srlgformat/srlgFormatMappings

Sample request

A response code of 200 indicates that the request succeeded. Upon deleting the mappings, the changes will start reflecting as part of the GET nsi/srlgformat and GET nsi/srlgformat/srlgFormatMappings response.

A sample request body to delete mappings is provided below.

{
  "data": [
    {
      "id": "subNetwork::NewSubnetwork2Region",
      "type": "subNetwork"
    },
    {
      "id": "subNetwork::NewSubnetwork1Region",
      "type": "subNetwork"

  ]

Use the delete Subnetwork mappings with caution. Subnetwork mappings are used to interpret the srlg applied in system. For Auto-assignment to work, the system considers subnetwork tagged to the parent networkConstruct and gets the value of the tag from subnetworkMapping. PATCH {NAVIGATOR_MC_HOST}/api/v3/networkConstructs/{id}

Shareable SRLG is used with FB profile. There are two ways to provide SRLG value.

  1. SRLG value with REST input

  2. Autofill of SRLG value

SRLG value with REST input

The user can provide SRLG values as Navigator MC defined format. Navigator MC defined format can be structured or opaque. It can be decimal. SRLG values will be validated against Navigator MC predfined format and transformed into decimal value. Transformed decimal value will be invoked in CLI srlg value.

SRLG manual assignment

To manually assign SRLGs, use the SRLG API.

Sample request

PUT {NAVIGATOR_MC_HOST}/ifd/api/v2/srlg

You must specify the following parameters:

  • resourceId

  • resourceName

  • resourceType (fres, networkConstructs or equipment)

  • srlgSet an object comprised of 'plannedStartDate' and the manual SRLG object. The date format is YYYY-MM-DDTHH:MM:SS.SSSZ. Multiple SRLG sets can be specified for different plannedStartDate(s) and one set without plannedStartDate can be specified. SRLG values can be supplied either as opaque values using srlgValues or as structured SRLG values using srlgStructuredValues.

  • applyToMateLink (optional) - For OMS service, if set this parameter to true, any changes made to the entity’s manual SRLGs will automatically apply to the OMS’s mate link as well. The default value is "false" and if you attempt to set this parameter to "true" for any non-OMS FRE, the request will fail.

If resourceName is being used for the SRLG assignment, then same values will be applied to all the entities found using resourceName. Below table illustrates how the lookup being done using resourceName.

resourceType resourceName Mapping

equipments

data.attributes.displayData.displayName over data.attributes.nativeName

fres

data.attributes.userLabel over data.attributes.mgmtName over data.attributes.nativeName

networkConstructs

data.attributes.displayData.displayName over data.attributes.name

tpes

data.attributes.displayAlias over data.attributes.nativeName
This API is available when SRLG format is configured as Structured or Opaque. If the SRLG Format is configured as Structured, SRLG values provided in opaque notation can be computed back to a Structured SRLG, otherwise the request is not accepted and validation errors are generated. On the other hand, if the SRLG format is configured as Opaque, values that can convert into the system display format and can fit in 32-bit number can be accepted.

A response code of 200 indicates that the SRLG is updated.

A sample request is provided below.

{
  "data": {
    "attributes": {
      "resourceId": "2000925292613460342",
      "resourceType": "fres",
      "srlgSet": [
        {
          "manual": {
            "srlgStructuredValues": [
              {
                "subNetwork": "NewYorkRegion",
                "riskType": "Conduit",
                "riskValue": 80023
              }
            ]
          }
        },
        {
          "plannedStartDate": "2018-09-26T10:30:01.607413Z",
          "manual": {
            "srlgValues": [
              "59520495"
            ]
          }
        }
      ]
    }
  }
}

SRLG auto-assignment to resources

To add SRLG auto-assignment to resources, use the SRLG API.

Operation considerations:

  • Navigator MC is configured to apply auto-assignment (in the SRLG Format isEnabled is set to true and formatType is set to Structured).

  • Auto-assignment is an asynchronous operation and you can query the job status to determine the status of the operation.

  • To auto-assign SRLGs in Navigator MC-managed resources, you must make separate requests for each EntityType (networkConstructs, equipments and tpes).

  • Navigator MC only allows one auto-assignment, clear auto-assignment, propagation, or write to network operation to be running at any given moment.

  • Navigator MC will consider the entities that qualify for the filter criteria defined in assignableEntityConfigurations of the SRLG Format.

  • Navigator MC will skip those entities where the SRLGs are already auto-applied.

  • Navigator MC will automatically select the subnetwork/Controller identifier from the parent networkConsturct. A prerequisite is to tag the networkConstruct (Network Element) with a subnetwork and ensure that the subnetworkMapping is defined using the GCS mapping described in section Configure Navigator MC for multiple subnetworks.

  • If Navigator MC is not able to compute the SRLG automatically for an entity instance, Navigator MC will mark the auto-assignment failed for that entity and will move to the next entity.

  • If Navigator MC is restarted, the auto-assigned values will be retained.

  • There will be separate pools on the basis of entity domain to manage uniqueness of the SRLG. The uniqueness index for the SRLG Format will be subnetwork+riskType.

  • The auto-assigned SRLG values will be unique to a specified pool.

You can trigger auto-assignment to resources maintained in the Navigator MC inventory as follows:

  • All applicable resources of a specified type (equipments, networkConstructs, tpes, fres) in the entire network.

  • All applicable resources of a specified type and riskType (for example, Add/Drop Bank).

  • All applicable resources of a specified type (equipments, networkConstructs, tpes, fres) and a region (Refer Region based auto assignment section below)

The default entity instance filter and considerations for auto-assignment are as follows:

  • equipments

    • ADD-DROP Bank: equipment where cardType is PEC: NTK723AA or NTK720CA

    • Line Module: equipment where circuitPack is NTK762MA, NTK762EA or NTK761AA (T-series, only)

    • ROADM Degree: cardType: RLA PEC (to be filled by CI) is NTK722AA

  • networkConstructs

    • Photonic Node: networkConstructs where memberFunction is ROADM. Only assigned to the primary shelf.

  • FREs: none

  • TPEs: none

A response code of 202 indicates that the request is accepted and will be processed in the background.

A sample request is provided below.

{

    "op": "auto_assign",
    "attributes": {
      "resourceType": "equipment"
    }
  }
}

Auto-assignment is an asynchronous response. The success response returns a job identifier. The job status for the job can be accessed using the following API: GET {NAVIGATOR_MC_HOST}/ifd/api/v2/srlg/job/{jobId}/details

Region based Auto-assignment

  • Auto assignment can be done region basis on Network Constructs and Equipments only

  • Scenario for Network Construct

    • There are multiple NEs belonging to different regions (say East, West, South, North)

    • When user triggers automation for a particular region (say East) then auto assignment should be applied only on NEs belonging to East region only.

    • If user triggers auto assignment on network (after step 2) then NEs of East region are skipped because they were already auto-assigned with SRLGs

  • Scenario for equipments is same

  • When auto-assignment triggered against a region (which doesn’t exist in SrlgFormat), then there are 2 cases:

    • Region tagged against a NC - auto assignment is applied successfully because a NC is found under that region

    • Region not tagged against a NC - auto assignment will return 0 entities processed

  • In short, region validation is not being performed against SRLG Format, but if a NC has tag with provided region, it is considered for auto-assignment

  • If No NE found for input region, auto assignment operation is shown as completed but with Zero entities processed.

SRLG Write to Network

Once SRLG assignment (Manual/Auto/Propagate) on resources maintained in Navigator MC inventories is completed, you might want to realize the assigned SRLGs on the nodes (write SRLGs to Nodal entities).

Operation considerations:

  • Only supported for 6500 packet devices version 13.0 and above

  • RSVP-TE must be enabled on the node

  • Navigator MC is configured to apply write-to-network (in the SRLG Format isEnabled is set to true).

You can trigger write to network operation in the following ways:

  • Given IP-Link. Input required: resourceType=fres and resourceId={freId}

  • All IP-Links on a single networkConstruct. Input required: resourceType=networkConstructs and resourceId={ncId}

  • All IP-Links on the entire network. Input should not provide resourceType and resourceId.

  • All IP-Links of a particular region of the network. Input should not provide resourceType and resourceId.

Functional aspects of Write To Network

  • Write to network operation depends on resources having SRLG Mismatch. In this release SRLG mismatch is computed for IP-Links only. Hence write to network will cater end-points of IP-Links.

  • Write to network operation will re-synchronize all the nodes, where-ever SRLGs have been pushed on end-point.

  • Write to network operation on a IP-Link might result in pushing SRLGs on all the end-points. Since end-points belong to different Nodes, hence will re-synchronize multiple Nodes.

  • There could be cases where number of SRLGs are higher than maxAllowedSrlgs, even after applying pruning algorithm. In such cases last 'n' SRLGs will be removed and Job details would capture such entities.

POST {NAVIGATOR_MC_HOST}/ifd/api/v3/srlg

A sample request is provided below.

    "op": "write_to_network",

     "resourceType": "fres",
      "resourceId": "-3700187992703639354"
    }
  }
}

Maintain External Pool of Srlg Values

Navigator MC allows you to auto-assign SRLG to the entities managed by Navigator MC.

External Pool of SRLG Values IFD API

You can use this API to assign any srlg value from pool or release any srlg value(pre-assigned) from pool according to the requirement. In these APIs, user label is given for the reference of a user to correlate the external srlg value with the user label set up.

POST - {NAVIGATOR_MC_HOST}/ifd/api/srlg/externalSRLGs

Assign Operation

Here in Assign External Srlg, following things are important:-

  • Data,Op and Type are mandatory fields in Request.

  • Label is mandatory for future reference in Request.

  • Srlg Fields are used to assign the value of external srlg from the type of pool required according to the srlg format parameters.

  • Srlg Fields parameters needs to be in line with Srlg Format set up.For Example,if riskType and Region are used in Srlg Format for External Pool they needs to be in line/match in this request.

  • In response, Structured as well as opaque values will be returned corresponding to the srlg value.

  • This API operation will return the next available External Srlg Value from Pool.

  • User can now set a GCS configuration to get SRLG Job notifications as per the set time interval.

  • This comes handy when a job is taking some time to finish and user wants to know whether it is running or not.

  • User needs to specify time in seconds in configuration, recommended to provide in multiples of 10.

  • By default value is -1, which denotes only start and end notifications of Job will be sent over Kafka topic.

  • If negative values specified, time interval notifications won’t be sent

  • If floating values are specified like 2.4, 12.9 etc, then floor value is taken i.e. 2 and 12.

IP Interface Node Share Srlg Calculation

For IP Interface while auditing,

  • Node Share SRLG is being calculated on the basis of Share srlg on source node as well as destination node srlg.

  • Link share srlg is being calculated using both Share srlg on source node as well as share srlg on destination node.

It is being made configurable using Global Config Service(GCS) APIs to define the policy that how node share srlg is to be calculated either using both source and destination or using source only.

You can define the policy flag in GCS service.

If in the config service, No policy is being defined we would be using Source and Destination Node share srlg to calculate node share srlg as default.

For Defining configuration through GCS, POST API need to be used in config v1.

Sample Request

[
    {
      "application": "configmgmt",
      "instance": "-",
      "partition": "configmgmt",
       "name": "fbProfile.autoNodeSRLGSetting.UseSourceAndDestination",
       "title": "fbProfile.autoNodeSRLGSetting.UseSourceAndDestination",
       "description": "FB profile Node SRLG setting. true = source node and destination node srlg values. false = source node srlg value.",

        "value":"true",
        "default": "true",

       "key": "configmgmt/-/configmgmt/fbProfile.autoNodeSRLGSetting.UseSourceAndDestination"
   }
]

Value in GCS needs to be defined according to the configuration :

  • True : Source and Destination Nodes

  • False: Source Nodes only

So according to the configuration, Value would be picked while processing node share srlg.
